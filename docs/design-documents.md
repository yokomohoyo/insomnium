# Design documents

A design document is a collection with an API spec at its heart: OpenAPI 3, Swagger 2.0, or AsyncAPI 2 or 3. Create one from the dashboard, import a spec file into one, or turn a collection into one with **Convert to Design Document** in its menu. **Convert to Collection** turns it back: the requests and tests stay, and the spec is put aside until it's a design document again.

It has three tabs, at the top:

- **Spec**: the spec, in YAML or JSON.
- **Debug**: the document's requests, as in any collection.
- **Test**: [unit tests](testing.md#unit-tests) for its requests.

## Spec

The editor checks the spec as you type, with [Spectral](https://github.com/stoplightio/spectral)'s OpenAPI rules, or its AsyncAPI rules for an AsyncAPI document. Problems are listed under the editor; click one to go to its line. The sidebar outlines the spec's paths, schemas and other parts, and **Toggle Preview** shows it as API documentation.

### AsyncAPI

An AsyncAPI document (one that starts with `asyncapi: 3.0.0` or `asyncapi: 2.6.0`) describes an event-driven API: its servers (Kafka, MQTT, WebSocket and so on), its channels, and the messages sent and received on them. The preview lists the servers, each channel with its operations (send and receive, or publish and subscribe in 2.x), and each message with its payload schema. **Generate Request Collection** is for OpenAPI and Swagger documents only.

### Not yet

- `$ref`s to other files or URLs. They're left as they are; refs within the document work.
- A visual editor, and specs in other formats (protobuf, GraphQL SDL).

### Your own lint rules

**Ruleset**, under the editor, says which rules the spec is checked with. **Choose a Ruleset File…** there picks a Spectral ruleset (`.spectral.yaml`, or `.yml` or `.json`) on your computer for this document; the choice stays on this computer. Without one, a `.spectral.yaml` at the root of the document's [Git Sync](git-sync.md) repository is used, and otherwise the built-in rules.

A ruleset can extend the built-in rulesets (`spectral:oas`, `spectral:asyncapi`, `spectral:arazzo`) and add, change or turn off rules:

```yaml
extends: spectral:oas
rules:
  operation-tags: off
  info-contact: error
```

A ruleset can come from a repository that others can write to, or from a file someone sent you, so it has to be plain data: custom functions, and extending a ruleset from npm, a file or a URL, aren't supported. When a ruleset can't be used, the first problem listed says why, and the built-in rules apply.

## Generate requests

**Generate Request Collection**, in the Spec tab, makes a request for each of the spec's operations, in folders by tag. Their URLs start with `{{ _.base_url }}`, set in the environment from the spec's servers.

After you change the spec, generate again to bring the requests up to date; it doesn't add a second copy. Each request remembers its operation, by `operationId`, or by method and path when the operation has none, and:

- its method and URL follow the spec, so a renamed path updates the request;
- parameters and headers the operation gained are added, and the values you've set stay;
- its name, body, auth, scripts, assertions and settings stay as you've made them;
- operations new to the spec get new requests, in their tag's folder;
- requests whose operation was removed from the spec are listed afterwards, and left for you to keep or delete.

New servers get an environment, and variables you've changed in an existing one stay. Requests generated by an earlier version of Insomnium are matched by method and URL the first time.
